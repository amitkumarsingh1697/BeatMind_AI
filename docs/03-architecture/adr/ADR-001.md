# ADR-001: Modular monolith plus GPU worker pool

| Status | Date | Deciders |
| --- | --- | --- |
| Proposed | 2026-10-28 | Founder and developers; drafted by Claude (delegated authority DEC-004, DEC-011) |

## Context

Three developers (DEC-006) must ship an MVP quickly, yet the product must scale to millions of users (DEC-011). Generation needs GPUs; everything else is ordinary web traffic.

## Options considered

1. Microservices from day one.
2. Modular monolith for all non-GPU work, plus a separate GPU worker pool joined by a queue.
3. Serverless functions for everything.

## Decision

Option 2. One Java service with enforced module boundaries (identity, library, generation, rights, provenance, billing, moderation, admin) and one Python worker type.

## Consequences

Fewer deployables, simpler debugging and one database transaction boundary. Modules can be extracted later because ArchUnit tests block cross-module access. The API scales by adding stateless replicas; GPU work scales independently on queue depth.
